# RetailHero — исторический A/B-анализ и uplift-таргетинг

Портфолио-проект на открытых данных X5 RetailHero. Цель — оценить средний эффект
SMS на вероятность покупки и проверить, может ли ранжирование клиентов по
предсказанному **дополнительному** эффекту улучшить ограниченный бюджет рассылки.
Автор **не проводил** исходную кампанию и не отправлял SMS; следующий policy A/B
спроектирован, но не запущен.

## Проверенные результаты после исправления RFM (05.11.2026)

Исторический эксперимент: **200 039 клиентов**. Конверсия контроля — 60,328%,
коммуникации — 63,651%; абсолютная разность **+3,323 п. п.**, 95% ДИ
**[+2,898; +3,748] п. п.** (z-тест двух долей, p≈6,62×10⁻⁵³). SRM при
предполагаемом соотношении 50/50: p=0,863. Подтверждение исходной схемы
рандомизации и точных окон из предоставленных файлов недоступно.

В отдельном ретроспективном 3-fold out-of-fold протоколе для топ-10% каждого
фолда получены следующие оценки прироста доли клиентов с покупкой:

| Политика | Uplift, п. п. | Разница со средним эффектом, п. п. |
|---|---:|---:|
| Случайная рассылка (ожидаемый средний эффект) | +3,323 | — |
| T-learner, корректный RFM | **+7,263** | **+3,940** |
| Наименьшие исторические расходы | +7,251 | +3,928 |
| Наибольшие исторические расходы | +1,461 | −1,862 |
| Наибольшая частота чеков | +0,769 | −2,554 |
| Самая недавняя покупка | +2,206 | −1,117 |
| Сумма рангов RFM | +0,976 | −2,347 |

Условный парный bootstrap (2 000 повторов, фиксированные OOF-скоры и
выбранные клиенты) даёт для **T-learner против случайного выбора** 95% ДИ
преимущества **[+2,707; +5,223] п. п.**. Однако разница **T-learner против
правила низких расходов** составляет только **+0,012 п. п.**, с 95% ДИ
**[−1,483; +1,594] п. п.**. Преимущество сложной модели перед этим простым
правилом **не установлено**. Правило низких расходов добавлено после знакомства
с результатами, поэтому сравнение исследовательское, не независимый финальный тест.

Наличие интервала выше нуля против случайной рассылки не доказывает перенос
эффекта на новых клиентов. Bootstrap не охватывает повторное обучение,
адаптивный выбор признаков и модели, а три фолда не являются тремя новыми
экспериментами. `target` означает **клиента с покупкой**, не количество чеков
или прибыль. Доход, стоимость SMS и маржа неизвестны.

Агрегаты пересчёта: [`results/crossfit_2026-11-05_corrected/`](results/crossfit_2026-11-05_corrected/).
Там же находятся manifest запуска с версиями, SHA-256 данных, количеством
итераций и хешами выбранных аудиторий. Индивидуальные OOF-строки локально
вычисляются, но в GitHub не публикуются.

## Исправление ошибки purchase_sum

В `purchases.csv.gz` каждая строка — товарная позиция, а `purchase_sum` —
**полная сумма чека, повторённая на всех его строках**. Старая версия
`scripts/build_rfm_features.py` использовала `SUM(purchase_sum)` внутри чека.
В результате совокупная денежная сумма истории была завышена в 10,336 раза.
Исправленный скрипт проверяет внутри `(client_id, transaction_id)` одинаковые
сумму, дату и магазин, отклоняет пропущенные ключи/невалидные значения и
берёт сумму чека ровно один раз. Затем по уникальным чекам считает клиентские
`sum`, `mean_check`, `spending_90d` и остальные RFM-поля.

Корректный полный проход обработал **45 786 568 товарных строк** и
**8 045 229 чеков** для **400 162 клиентов**. Вместе с CSV сохраняется
`final_stats.meta.json`: версия признаков `retailhero_receipt_total_once_v2`,
SHA-256 исходного gzip, схема и опорная дата. Валидация отказывается читать
старый/неполный RFM без этих метаданных.

## Модель и протокол

- T-learner: отдельные `HistGradientBoostingClassifier` для treatment/control;
  скор = `P(target=1|X,treatment=1) − P(target=1|X,treatment=0)`.
- 13 признаков: возраст, индикатор неизвестного возраста, пол и восемь
  предкампанийных признаков истории. Медианная импутация внутри обучающих
  пайплайнов, без доступа к проверочным исходам.
- `StratifiedKFold(n_splits=3, shuffle=True, random_state=20261030)`,
  стратификация по сочетанию `treatment_flg` и `target`. Две модели в каждом
  обучающем фолде, один OOF-скор для каждого клиента.
- В каждом проверочном фолде выбирается `ceil(0.10 × n)` клиентов;
  равные скоры разрешаются детерминированно по `client_id`, а не по `target`.
- Парный bootstrap пересэмплирует совместные категории внутри фолдов,
  сохраняя пересечения выбранных аудиторий. Это **условный** интервал для
  фиксированных политик.

Предкампанийный характер истории следует из описания набора данных;
индивидуальная дата SMS недоступна. `recency_days` рассчитывается относительно
дня после последней транзакции всей предоставленной истории, а не от
восстановленной «даты кампании».

## Воспроизведение

Рекомендуется Python 3.12.14 и `pip install -r requirements_repro.txt`.
Данные: [Hugging Face RetailHero](https://huggingface.co/datasets/pytorch-lifestream/retailhero-uplift/tree/main/data).
Сохраните файлы `purchases.csv.gz`, `uplift_train.csv.gz`, `clients.csv.gz` в `data/`.

```bash
python -m unittest discover -s tests -v
python scripts/build_rfm_features.py --input data/purchases.csv.gz --output data/final_stats.csv --memory-limit 2GB
python scripts/validate_crossfit.py --ab data/uplift_train.csv.gz --clients data/clients.csv.gz --rfm data/final_stats.csv --output outputs/crossfit --bootstrap 2000
```

SHA-256 исходных файлов из воспроизведённого запуска есть в
`results/crossfit_2026-11-05_corrected/run_manifest.json`. Требуются несколько
гигабайт свободного места для DuckDB и результатов. Подробная методология —
[`docs/crossfit_validation.md`](docs/crossfit_validation.md).

## Архив прежних результатов

Публикация от 30.10.2026 с ошибочным RFM дала **6,842 п. п.** на трёх фолдах;
число воспроизведено независимым аудитом, но денежные признаки в той версии
неправильны. Архив: [`results/crossfit_2026-10-30/`](results/crossfit_2026-10-30/).
Сохранённые holdout-ноутбуки (`notebooks/RetailHero_AB_Uplift.ipynb`,
`notebooks/RetailHero_AB_Uplift_RFM_executed.ipynb`) относятся к прежнему,
адаптивно выбранному протоколу и **не являются источником текущих RFM-чисел**.
Они оставлены для истории разработки, но не должны запускаться для получения
итоговых результатов после исправления. Канонический entrypoint — два скрипта
выше. Не следует менять 6,842 на 7,263 в старом notebook output без исполнения.
